Claude Programs a Robot in Weight Space

No gradients and no training. Claude changed one matrix inside π0.5, the model driving the robot, and success on 50 RoboCasa tasks rose from 51.9% to 65.1%.

Jack Sun Kelip

The setting

Neural networks are normally changed by training: choose a loss, run gradient descent, and let the weights move. MIT's Sparks of Weight-Space Programming (Takehi et al., 2026; a blog post, not peer reviewed) tried something else. GPT-6 Astra read and rewrote weights directly, and in one experiment changed 0.016% of a small language model's weights to raise its MATH-500 score from 7.9% to 48.1%. We wanted to know whether this reaches a model that drives a robot, so we tried it with Claude Opus 5.5.

The model is π0.5, a vision-language-action model from Physical Intelligence. It takes camera images, the robot's state and a text instruction, and uses flow matching to produce a 50-step action chunk. We used the public checkpoint from the RoboCasa team, pi05_pretrain_human300, converted to PyTorch, and ran it in RoboCasa's simulated kitchens with the settings of the official evaluation script. The rules were simple:

  • Claude may change π0.5's weights and the processing around the model.
  • No gradient descent and no training.
  • Every change is tested in closed-loop rollouts against the unmodified model, on the same tasks and seeds.

Claude works on the weights through code: it loads tensors, reads activations, computes a change, writes the new matrix and runs rollouts to check it. A person set the goal and the rules, and questioned the results along the way. Claude chose what to look at, wrote the analysis code, ran the experiments and picked the edits.

How Claude found it

The path was not a straight line. Claude began with the MIT approach and it failed. What the edit ended up fixing was a mismatch between the images π0.5 was trained on and the images it sees in evaluation.

1. There was no single failure to fix

Claude started from 1,478 recorded π0.5 episodes from an earlier survey, 741 of them successful. The failures fell into six types, and the largest was 24%. In the MIT experiment that inspired this, one failure mode accounted for 93% of the answers, so a single direction could carry the fix. Here nothing stood out.

2. The plans start slow

The recorded action chunks did show a pattern. In closed-loop states, the first 5 planned steps moved 0.242 per step, while steps 20–35 moved 0.448. π0.5 replans every 5 steps, so it only ever executes the slowest part of each plan.

3. The MIT recipe did nothing here

Claude then tried the approach from the MIT post: find a direction in the action expert that separates good from bad behavior, then remove it. The 24 candidates, such as stuck versus moving, left the opening speed at 1.00 times the original, with at most a 3% difference. A closed-loop run of the failure-minus-success direction moved success from 20 to 24 of 80 episodes (p = 0.29).

4. An accident

The recordings store images as JPEG. When Claude recomputed actions from those images with the same noise, to check its own pipeline, the actions differed from the recorded ones by about a third, and the openings got faster. Recomputing from lossless PNG recordings matched bit for bit. So the pipeline was fine, and the model was reacting strongly to JPEG compression.

5. Same state, same noise, two images

That raised a better question. π0.5 was trained on videos: the official dataset is H.264 (x264 CRF 23, yuv420p). Evaluation feeds it uncompressed renders, both in the official script and in ours. So Claude restored simulator states from the training demonstrations, rendered them again, and compared each render with the decoded training frame of the same state. The two differ by about 40 dB PSNR. You can try telling them apart here:

The model treats them very differently. Figure 1 shows the planned speed for the same states with the same noise. On training frames, the opening speed is close to the human demonstration. On renders it drops by about a third, and it recovers later in the chunk. Only the opening gets executed, so the robot keeps running the slow part. In the first check on 70 states from 6 tasks, the opening speed was 0.541 for the human, 0.542 on training frames and 0.356 on renders.

6. It is sharpness, not noise

White noise with σ = 3 changes pixels by 2.39 on average and actions by 0.011. A blur with σ = 0.8 changes pixels by a similar 2.68 and actions by 0.081. Opening speed rises steadily with blur: 0.242, 0.342 (σ = 0.5), 0.540 (σ = 0.8), 0.607 (σ = 1.2). The wrist camera matters most: swapping only that view to the training frame takes the speed from 0.356 to 0.507, against 0.407 for the right camera and 0.370 for the left.

In token space, a single direction works like a knob. Pushing the projection layer's bias along the mean render-minus-training-frame difference moves the opening speed smoothly from 0.226 to 0.647. Images sort along that direction by sharpness (wrist camera): white noise 36.1, raw render 35.9, JPEG95 33.0, JPEG90 26.9, blur 0.6 25.7, training frame 22.1, blur 0.8 20.3, JPEG50 7.5.

7. From an image effect to a weight edit

SigLIP's patch embedding is linear, so multiplying it by a Gaussian kernel is the same as blurring every patch. That first edit took 16 practice tasks from 45 to 73 of 160 successes. Claude then searched more widely, over 4,480 practice episodes in total: weight edits at every stage of the network, changes to the processing, and combinations of the two.

The closer to the image, the stronger the effect. Out of 80 episodes, against 20 for the original model, edits on the projection layer reached 39–42 and SigLIP's last layer reached 31. Backbone layer 12 reached 28 (p = 0.057). Edits inside the action expert stayed at 23–24, which is within noise. Adding other changes on top of the fix, such as more denoising steps or attention offsets, never beat the fix by more than noise, and a few made it worse. That covers only the edits we tried, so it doesn't prove the action expert can't be edited usefully.

The edit

SigLIP1152-dim tokens
Projection layerW, 2048 × 1152. The only tensor changed
PaliGemma backboneGemma 2B
Action expertGemma 300M
Flow matching50-step action chunk

The projection layer maps SigLIP tokens into the backbone: y = W x + b. The edit removes three input directions from it and leaves the bias alone:

W′ = W (I − V Vᵀ)
# in code
W = W - (W @ V) @ V.T

V came from data, without gradients:

  1. Take 254 simulator states from the training demonstrations of 27 tasks, none of them among the 10 held-out test tasks.
  2. For each state, get two images: a fresh render and the decoded training frame. Three cameras with 256 tokens per image give 195,072 token pairs.
  3. Subtract each pair after SigLIP's post_layernorm, compute the second-moment matrix of the differences, and keep the top 3 eigenvectors.

On 305 states from 27 other tasks, the opening speed goes from 0.377 to 0.576, against 0.585 on training frames. The gap to the actions planned from training frames falls from 0.053 to 0.025. Three directions are close to saturation: two give 0.529 and five give 0.580.

Most of the matrix's behavior survives. Its largest singular value stays at 14.93, and a random direction keeps 99.8% of its gain (median). The three chosen directions fall from a gain of about 1.9 to 0.002. The edit isn't harmless, though: those directions also hold 27% of the energy in training-frame tokens, and the distance between render and training-frame tokens shrinks by only 19%. The two kinds of image don't become the same to the model.

The directions matter. In the same matrix, with the same norm change (8.2%), three random directions with matched gain leave the speed at 0.377 and 0.376, which is the same as no edit. The three directions with the most token energy break the model (0.077). In closed loop, over 80 practice episodes where the original model gets 20, the random directions get 18 and the high-energy directions get 0, against 39 for this edit.

Where the change is largest isn't where it works. Column 725 of W holds 18.1% of the change's energy and was rewritten by 133%, and dimension 725 is where renders and training frames differ most on average. We expected it to be the key. It isn't: zeroing that column gives 0.382, flipping its sign gives 0.414, and zeroing the top 5 columns (a 7.6% norm change) gives 0.385. Random columns give 0.377. We don't yet know which part of the three directions does the work.

The full results

The gain isn't uniform. Grouping tasks after seeing the results, so this is only descriptive: pick-and-place went from 56.5% to 78.5%, buttons and knobs from 37.1% to 43.6%, and everything else from 58.3% to 70.7%. OpenOven stayed near zero. The 18 official Atomic-Seen tasks went from 51.9% to 65.8%.

Using tasks to estimate the directions doesn't seem to inflate the gain. The 19 tasks used for that went from 56.1% to 64.7%, and the 12 tasks that were not used to estimate directions, for offline evaluation or in practice went from 47.1% to 64.6%.

Not every pair is an exact pair. In 924 of the 1,000 pairs, the two episodes start from a bit-identical simulator state. For a few tasks, mainly kettle, sink and stand mixer, environment creation isn't fully determined by the seed. On the 924 exact pairs the result is 51.0% → 64.0% (+200 / −80, p ≈ 5×10⁻¹³).

The test set. Before the 1,000 fresh-seed episodes, we ran three candidates once on a test set with pass rules written in advance: 22 tasks × 30 episodes. The original got 35.2%, patch-embedding blur 49.2%, five directions 52.3% and three directions 53.8%. On the 10 tasks held out of every earlier step, three directions went from 47.7% to 68.0%. All three passed.

The three-direction edit isn't better than the blur. Its lead on the test set was probably a selection effect. On fresh seeds the two tie: 225 and 224 of 440 (+52 / −51 against each other). The difference is size: the blur changes the patch embedding by 44% in norm, and this edit changes the projection layer by 8.1%.

Is the baseline broken?

A 13-point gain from a small edit should make anyone suspect the setup, so we checked.

  • The official evaluation script also feeds uncompressed renders, and the official dataset is video. The mismatch comes with the official pipeline; we didn't introduce it.
  • Replanning, time limits, state format and action conversion match the official script. In 3 tasks, the state in our loop and in the training data are bit-identical for the same simulator state.
  • We ran the official stack itself: JAX weights, serve_policy and the official client's eval_env, on the target split, with 8 tasks × 20 episodes. It got 55/160 (34.4%) and our baseline got 59/160 (36.9%). The difference is −2.5 points with a 95% CI of about −13 to +8, so this only rules out a large offset.

A third-party leaderboard lists π0.5 at 39.6% on Atomic-Seen, while our baseline gets 51.9% on the same 18 tasks. We can't explain this gap, because the leaderboard doesn't state its settings or episode counts. Please don't compare the two numbers directly.

What this says about editing weights

What it shows

A language model can change a trained robot policy directly and make it better in closed loop, with no gradient descent and no training. The whole change is three vectors and one line of linear algebra, so anyone can read it, check it by hash and undo it. It held up on seeds and tasks that played no part in choosing it.

What it doesn't show

  • Claude didn't find the fix by reading the weights. The clue came from comparing training images with deployment images. Reading the action expert and applying the MIT recipe found nothing. The contrasts that recipe relies on, like failure minus success, have a cosine within ±0.11 of this direction (measured on JPEG recordings). Every closed-loop frame is equally sharp, so the difference doesn't show up between failures and successes. The weights were where the fix got written down, not where it was discovered.
  • The weight edit doesn't beat a simpler fix here. Without touching any weights, encoding frames with x264 in the loop gives about the same result: 70 of 160 practice episodes against 73 for the blur edit, up from 45 (p = 0.74 between them). The weight version only saves you from changing the input pipeline.
  • Moving faster isn't the fix on its own. Skipping the first 5 steps of each chunk gave 45 → 50 of 160 (p = 0.51). An action gain of 1.3 gave 20 → 23 of 80, and on top of the five-direction edit it lowered success from 42 to 30 (p = 0.012).
  • The explanation is a guess. A single image and the robot's state hold no velocity, so the model may have learned to read motion from compression softness. Closed-loop images are always sharp, so it would always think it's standing still and plan a slow start. The evidence: on training frames, this direction correlates with human speed (r = −0.24, −0.34 and −0.28 for the left, wrist and right cameras), and on renders of the same states it barely does (−0.05, −0.03 and −0.08). The correlations are moderate, and a direct test would need retraining.
  • Coverage is limited. These are 50 short tasks: 18 from official Atomic-Seen plus 32 others we picked. They aren't the official target50, and its 32 composite tasks are untested. Eleven tasks went down, though at 20 episodes per task some of that is noise.
  • Simulation only, one run. Nothing has run on a real robot. This is a single debugging run by one model, and we have no fine-tuning baseline at the same rollout budget.
  • Prior work. Three rounds of searching found no direct report of this image effect, but the search wasn't exhaustive. If you know of one, please tell us.

Questions we'd like to hear about

  • Can a language model fix faults that don't come down to an input mismatch, the kind no preprocessing step can reach? Every edit we tried inside the action expert failed, but we only tried a few kinds.
  • When is editing weights a better tool than fine-tuning? How would you compare them fairly at the same rollout budget?
  • How should an agent's edit be reviewed? This one changes 2.25 million numbers, and 87 episodes got worse alongside the 219 that got better. What should count as enough evidence before a change like this goes on a real robot?

If you train on video datasets

LeRobot-format datasets are commonly stored as video, so other projects may have the same gap. We have only tested one model on one dataset, so we don't know how common it is. The check is cheap:

  1. Restore a few states from your training data in your simulator, and render them the way your evaluation does.
  2. Run the model on the render and on the decoded training frame, with the same noise.
  3. Compare the first few planned actions. If they differ by much more than white noise of the same pixel size causes, try re-encoding frames in the loop and measure success.

Data and code

Everything is in the GitHub repository:

  • edit/: the exact edit, the script that applies it, and SHA-256 prefixes for checking (before c3c6ae81d4fa4956, after 102128668f8b1ba5).
  • results/: per-episode outcomes for the fresh seeds and the test set, every practice run, the official-stack check and the offline controls.
  • code/: the scripts for the main steps. estimate_directions.py reproduces the three directions (cosine 1.000000 with the published edit). The rollout harness isn't included, so the headline numbers need your own loop.
